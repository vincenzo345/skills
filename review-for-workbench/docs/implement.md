## What it does

`implement` pins the starting commit and dirty worktree, then maps every criterion to required evidence before editing. It normally claims an executable ticket. A fully specified direct request may instead use a compact in-turn execution contract when it clearly fits one session and needs no invented decisions; larger or uncertain work routes through `to-spec` and `to-tickets`. The skill works test-first at approved public seams, runs focused and complete checks, and reviews committed, staged, unstaged, and in-scope untracked changes. Fixes to blocking review findings trigger affected proof and review again before closure.

## Truthful completion

Each criterion receives a proof receipt with actual population, achieved level, result, artifact, and `passed`, `failed`, or `blocked`. Missing access or deployment may allow lower-level work to continue, but a ticket stays open when its own criteria require the missing proof. Overall status is bounded by unmet criteria, not the best result in the set.

Criteria are not rewritten to fit the implementation. A commit is created only when the user or repository workflow authorizes it, and a commit is a checkpoint—not evidence that deployment or the outcome succeeded.
