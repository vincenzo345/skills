# Claude–Codex Workbench parity scorecard

Last updated: 2026-09-18 (live v1.14.1 scored as v20.15; parity not met)

This is the running scorecard for the live Applications4Life Workbench investigation. Update it after every evaluated candidate, before beginning the next harness iteration.

## Rubric and acceptance bar

Scores are 1–5. Weighted total uses: factual/causal correctness 28%, evidence/calibration 22%, coverage/actionability 18%, Workbench fidelity 14%, clarity 8%, and efficiency 10%.

A passing Claude configuration must have a weighted total of at least 4.0, every dimension at least 4.0, median peak request context no more than 150,000 tokens, median duration no more than 1,500 seconds, and all four hard gates passing. The comparison goal is to meet or exceed Codex's quality while retaining Claude's efficiency advantage.

## Current assessment

Claude v18 C0 remains the champion. Its 4.706 weighted total exceeds Codex's 4.522; every dimension clears 4.0, all four hard gates pass, and resource ceilings pass.

The v19 installed canary scored 4.052 from the same frozen blind judge. It passed all hard gates and stayed below both ceilings, but failed the per-dimension bar in factual/causal correctness (3.8), Workbench fidelity (3.5), and efficiency (3.6). Its strongest improvement was live, route-specific evidence: it attributed cold initialization to the page-preview journey, found init timeouts, reproduced a parallel-fetch regression, and identified the warm App Runner routing asymmetry. Its main defects were causal overstatement from non-identical page windows, an absolute claim that App Runner would remove the tail despite untested scaling, warming the deployed preview cache despite a read-only constraint, an unproven clean-worktree claim, and excessive Workbench duplication. The overly broad Stop-hook match on temporary probes was fixed and globally redeployed after this scored run, but that post-run fix does not alter the score.

The v20 installed canary was much faster and smaller, but failed the user's explicit lifecycle instruction. Claude found the existing same-day item and said it would not start a fifth pass, despite “ignore any active work items and start new.” It then repeated inherited causal and absolute claims that the new global contract would have prohibited if freshly evaluated, and mismatched the option number in its implementation question. The conflict came from Workbench's unconditional “never duplicate resumable work” rule; v20.1 makes explicit start-new instructions authoritative and requires inherited claims and final identifiers to be rechecked.

v20.1 corrected the lifecycle failure: it created a separate item, used the one-command proposal handoff, and reached `awaiting-acceptance`, raising Workbench fidelity to 4.6. It still treated cache-warming GETs as ordinary read-only usage, exceeded the token ceiling, and over-attributed differences between different endpoints/runtimes to the runtime alone. The next candidate moves only the deployed-application mutation boundary into a narrow pre-tool guard, limits options-only work to one measurement family by default, and explicitly rejects shared code across different endpoints as a like-for-like causal experiment.

v20.2 proved the deployed-application guard changes behavior: Claude made no live application probe and finished in 122 seconds. It nevertheless reinterpreted the prior candidate's new item as satisfying this invocation's explicit start-new command, so fidelity fell back to 1.2; it also repeated inherited causal overclaims instead of recalibrating them. v20.3 mechanically requires compact routing before old Workbench state can be inspected when the current request explicitly says start new, and restores environment-first ordering as a concise global rule.

The v20–v20.2 runs used the shared Applications4Life checkout and could see artifacts created by earlier candidates; they are retained as useful diagnostics but are not valid candidate comparisons. v20.3 is the first corrected clean run: a fresh secret-scrubbed clone at `7ab38557` with no `.workbench` and no project-local skill shadowing. It created and completed the requested proposal without live probing, but the code-change Stop hook treated an external temporary phase JSON as a product edit after the terminal review marker. The forced second review found real omissions, edited the immutable accepted artifact, restored it, and left an unaccepted addendum. v20.4 restores trusted terminal-marker suppression and makes the pre-accept skeptical review boundary explicit.

v20.4 removed the post-accept cycle and improved to 4.474, only 0.048 below Codex overall. Evidence, coverage, Workbench fidelity, clarity, token use, and duration all passed; factual correctness remained 4.3 and efficiency 3.8, while the environment-order hard gate still failed. Transcript inspection found six avoidable guard denials: the start-new guard rejected a valid root-level routing JSON three times, and the read-only guard mistook three `grep`/`git show` reads of script files for script execution. The compact handoff then rejected natural `summary`/`classification` aliases after accepting the mechanical frame, causing one recovery path.

v20.5 passed every hard gate but regressed to 3.936. It overclaimed that transfer was irrelevant from small-image evidence, inferred that first views dominate from cache-write counts, and called pre-rendering the only option that targets the dominant case without establishing that dominance. The final also omitted a complete effect/cost/premise treatment for each option. Mechanically, a valid Next.js source path was percent-encoded and then rejected as nonexistent after the framing handoff had already advanced; an inline passive log parser was also denied merely because its query text named the page-preview route. Those deterministic defects are being fixed, but the unsupported causal claims are model-output variance rather than evidence that another prompt clause will improve the general harness.

v20.6 used interactive background mode rather than the established non-interactive evaluation protocol, so it is retained only as a diagnostic. It exposed a structural gap: the installed Workbench was lifecycle-complete but contained no self-contained performance-investigation method, so Claude improvised the diagnostic discipline that the high-scoring v18 campaign prompt supplied explicitly.

v20.7 used the correct clean non-interactive protocol and the new bundled performance method. It improved efficiency to 3.6, finished at 104,417 tokens in 423 seconds, passed every gate, produced a concise artifact without write retries, and avoided the prior full-parse and unbenchmarked-renderer claims. It still treated topology as runtime proof: possible Lambda fan-out became guaranteed separate environments, absent Terraform endpoints became the live NAT path, inline rendering became CPU-bound, and one log trace was said to eliminate whole option branches. Because the method already prohibited each class, the next change promotes that generic rule to the global system contract rather than adding task-specific examples.

v20.8 promoted the topology-versus-runtime invariant into the global contract and made compact handoffs indexes rather than duplicate proposals. Factual correctness rose to 4.3, evidence calibration to 4.5, clarity to 4.7, and total to 4.324 while tokens fell below 100k. The remaining losses were largely mechanical: Claude attempted three reads before creating the explicitly new item, wrote routing and phase JSON to the operating-system temp directory despite the workspace boundary, narrated descriptive read permissions as granted actions even though the governed receipt correctly granted none, and repeated too much of the artifact in the final. The cache-read diagnostic also referenced a cache-write warning, so it did not fully discriminate the proposed hypothesis.

v20.9 fixed those lifecycle mechanics: the bundled method could be read before routing, all helper files stayed inside the disposable workspace, authorization matched the prepared receipt, the item completed in one terminal handoff, and Workbench fidelity rose to 4.9. It still scored only 4.110. The causal review found three general errors: it treated serial prefetches as additive to time-to-first-page without proving the UI waits for the full window, suggested concurrently initiated cache warming could help the same first open, and claimed a browser waterfall plus aggregate Lambda metrics could distinguish cache tiers and internal processing stages. The recorded environment-order failure is an evaluator-extraction artifact: the execution card contains all five coordinates before option ordering, but a standalone JSON tool result caused the gate parser to discard surrounding prose. The run remains rejected on its 3.7 factual score and 3.6 efficiency regardless.

v20.10 corrected milestone scope, prerequisite timing, and measurement resolution. Coverage rose to 4.7 and the final correctly asked for cache-branch and internal-stage instrumentation instead of treating a waterfall as sufficient. It regressed mechanically because the explicit start-new guard denied the `Skill(workbench)` invocation that contains the helper contract; Claude then guessed the command, input schema, and ID format through multiple failed calls. The final also called absent pre-generation the structural cause despite leaving the dominant segment unknown, and called it the only option affecting the first page even though cold-start and CPU options also affect that milestone. The guard now permits loading Workbench before lifecycle creation, and the terminal review explicitly checks milestone, temporal, measurement-resolution, and exclusive-cause consistency.

v20.11 proved that allowing Workbench skill loading removes the helper-schema and ID probes: the lifecycle started with one valid compact call, and the terminal review caught and retracted two real milestone errors. However, Claude still attempted two repository reads before loading the explicitly named skill, a local benchmark had been falsely blocked by route words in its docstring, and discovery expanded to 53 tool calls. It then overstated two independent document objects as two full-document parses, inferred the NAT path from repository topology, and bundled memory with provisioned concurrency. The next candidate injects the Workbench-first route at prompt submission, makes the read-only guard detect network operations rather than domain words, and enforces the documented bounded evidence budget mechanically.

v20.12 validated all three mechanical changes: Workbench was the first tool, routing succeeded without schema/ID probes, discovery was capped, peak context fell to 93,279, and fidelity returned to 4.9. Efficiency reached 3.9, just below its floor. The remaining quality failure was semantic: no in-repo prewarmer became “a first open always misses both tiers,” conflating first browser view with first-ever object request; the final also dropped the source-snapshot qualifier from its CloudFront statement. The next candidate adds a generic cache-lifetime distinction and requires provenance qualifiers to survive final compression, while allowing the already-safe shell form used to read the bundled method.

v20.13 preserved clean startup and cache-lifetime calibration, but the model introduced different violations of rules already present: it assumed sequential Lambda calls reuse one warm environment, described an option as helping the warm branch after calling it inert there, and labeled prewarming the largest available win without deployed measurements. This pattern shows that adding low-salience reference prose is not reliably constraining final synthesis. The final candidate moves the proven bounded-investigation invariants into prompt-time context and lowers the mechanical evidence ceiling from 30 to 24 calls.

v20.14 moved the proven generic invariants into prompt-time context and improved evidence calibration to 4.4 and factual correctness to 4.1. It nevertheless scored 4.072 because malformed compact routing and handoff inputs caused repeated repair calls, the 24-call cap then stopped the planned benchmark, and Workbench fidelity/efficiency fell to 3.8/2.1. The cap is reverted to 30 in the installed harness because it amplified unrelated lifecycle variance. Across clean installed-only runs v20.3–v20.14, the best total remains v20.4 at 4.474—0.048 below Codex—and no configuration clears every 4.0 dimension consistently. The task-specific v18 campaign prompt proves Claude can exceed Codex (4.706), but the portable installed harness has not reproduced that result reliably. Further clauses now move failures between causal calibration, lifecycle mechanics, and efficiency; continuing on this single fixture would be overfitting rather than evidence of general parity.

v20.15 scores the exact globally installed v1.14.1 combination after restoring the 30-call ceiling. It reached 4.412 with 95,967 peak tokens and 373 seconds: 0.110 below Codex overall, while using 37% fewer peak tokens and 45% less wall time. Evidence calibration (4.8) and Workbench fidelity (4.7) were strong. Remaining losses came from two bounded causal overstatements (calling the extra context operation a doubling, and overstating what an unpinned pdfplumber dependency leaves unknown), repeated artifact/final prose, sequential shell calls, and one prevented pre-start inspection. Efficiency remained 3.7, so this exact live configuration does not meet the every-dimension acceptance bar.
