---
name: grill-with-docs
description: A relentless interview to sharpen a plan or design, retaining requirements in the effort and qualifying vocabulary and decisions in project domain docs.
disable-model-invocation: true
---

1. Read the configured tracker and [shared work-record contract](../setup-repo/WORK-RECORDS.md). Resume the identified effort; create one stable request-named effort only for a new request. Read its discovery record and current decision when present before asking again. For local writes, use [local planning operations](../wayfinder/LOCAL-PLANNING.md); remote decision answers remain on the configured tracker.
2. Call the Skill tool for "feature-planner" to investigate the relevant code and draft an implementation approach before the first interview round. If the harness has no Skill tool, read and apply the installed feature-planner SKILL.md. Supply the request and retained effort context. Treat its plan as a proposal, not an accepted decision; preserve its evidence, assumptions and unresolved input. If it stops on a blocking question before a final plan, carry the question and available findings into step 3; resume feature-planner with the answer when available. If the target or intent is too unclear to guide discovery, resolve the minimum input needed first. If the skill is unavailable, report that and stop rather than silently substituting a different workflow.
3. Before or during the interview, when the planner or interview identifies a specific unresolved, consequential UI, architecture, data-model or module choice that needs specialist design, explain the question and call the Skill tool for "design" before dependent interview questions. If the harness has no Skill tool, read and apply the installed design SKILL.md and its relevant branch. Pass the partial or proposed plan, supporting evidence, accepted constraints and effort reference. Design can precede a completed initial plan; skip it when an established path resolves the choice. Preserve the user's authority over consequential decisions and retain design findings in the existing effort. If design is unavailable, report the missing dependency, retain the question as open and leave dependent work unready.
4. Call the Skill tool twice, for "grilling" and "domain-modeling". If the harness has no Skill tool, read and apply each installed SKILL.md. Refine the proposed plan with the user, using its research to answer factual questions and focus the interview on consequential choices. Apply step 3 as new questions arise. Continue targeted research when answers expose gaps. Preserve the interview's rounds and human judgment; distinguish recommendations from accepted decisions. A reply continues the unresolved question; record missing human choices as open questions until answered.
5. When design yields accepted choices, call the Skill tool for "feature-planner" again with those choices, evidence and the existing plan, or apply its installed SKILL.md when the harness has no Skill tool. Review and revise the affected approach, interfaces, assumptions, failures and verification without reworking unaffected decisions. Bring new consequential choices back to the interview. If needed input remains unavailable, retain it as open and keep dependent work unready. Without design, re-evaluate the refined approach proportionally against the agreed outcome and relevant implementation, failure and verification concerns.
6. Persist the proposed and refined plan, ordinary requirements, findings, constraints, and open questions in the effort's discovery record as they become clear. When working a Wayfinder decision, keep its authoritative answer in that decision and link to it from discovery instead of copying it. Include the actual supplied answer or a faithful concise account; never manufacture approval. Shared terms still belong in the configured glossary, and only qualifying decisions become project ADRs.
7. At the boundary, link the effort and refined plan, summarize the approach and its supporting evidence, identify unresolved input, and name the next invocation. Carry those same references into to-spec. When the complete scope meets [ticket sizing and readiness](../setup-repo/TICKET-SIZING.md), the user can invoke implement directly. A resolved interview does not approve an implementation breakdown or begin implementation.
